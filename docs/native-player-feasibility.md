# 原生播放器迁移可行性评估

评估日期：2026-11-13。范围为当前 macOS 客户端，目标是播放画面、控制界面和交互均不再依赖 WebView，同时保留现有功能。

**结论：可行，值得按阶段推进；完整功能对齐属于播放器迁移，不能当作替换一个视频控件。** 最大的确定性收益是统一播放状态、输入和窗口生命周期。性能收益需要原型实测，尤其不能预先承诺首帧更快、CPU 或内存降低某个百分比。

本次完成源码分析和依赖兼容性试验，没有修改应用实现或项目依赖，也没有启动原生播放器原型。

**已核实的基础条件**

- 项目在 `go.mod` 锁定 MyGo `v0.8.4-0.20261107092838-4219d257423d`。该版本 `ui.Video` 主要承载逐帧画面，没有声音或内置系统视频解码，不能直接替换当前播放器。
- MyGo v0.9.0 的 `ui/video` 已支持带声音的系统播放。在 macOS 使用 AVPlayer，支持 MP4、HLS、跳转、倍速、音量、静音、就绪和缓冲状态，并将解码画面交给 GPU 渲染。[官方文档](https://github.com/egoist/mygo/blob/v0.9.0/docs/ui/video.md)
- v0.9.0 同时提供 `ui.NativeView`，可以在 MyGo 布局中放置平台原生视图并覆盖原生控件，因此 AVKit 视图也有集成路径。[对应源码](https://github.com/egoist/mygo/blob/v0.9.0/ui/webview.go)
- 使用临时 `-modfile` 将 MyGo 指向 v0.9.0，全部包的编译及现有 `go test ./...` 均通过。正式 `go.mod`、`go.sum` 保持原值。这个结果说明已有代码的初步兼容性良好，不代表原生视频、画中画或线上媒体流已验收。
- 当前 WebView 由 `main.go` 创建，`MediaHost` 通过 JS 发送播放场景及命令。推荐流、播放控件、评论和弹幕仍有实质性逻辑位于 frontend。

**功能复用与迁移范围**

| 功能 | 可复用部分 | 迁移工作与主要风险 |
| --- | --- | --- |
| 上游播放地址、清晰度、账号和备用设备 | `internal/ipc/playback.go`、SDK 与备用设备逻辑 | 原生控制器直接调用既有 Go 服务，继续处理超时、取消和过期响应 |
| 解密、音画合并、媒体缓存、HLS | `internal/media` 和现有 FFmpeg 流程 | 原生引擎读取现有本地媒体服务；仍须验证实际编码、未完成媒体、Range 和 seek |
| 播放/暂停、进度、倍速、音量、适配比例 | v0.9.0 已有基本播放 API，MyGo 已有交互组件 | 重写控件及键盘事件，明确暂停意图、当前集、画质与时间点的一致性 |
| 上下切剧、连播、跨季、预加载 | 推荐队列、后端预加载窗口、缓存及诊断可复用 | JS 三槽播放器、首帧等待、输入排队、预热和资源释放需要迁移；属于高风险部分 |
| 观看历史与云端双向同步 | 现有 library/store 与账号隔离逻辑 | 重接定时、暂停、seek、换集、关闭、退出时的进度上报；保留会话序号与旧回调过滤 |
| 点赞、收藏、评论、回复 | Go 服务及数据模型 | 原生重建控件、分页、输入、错误反馈与数据失效通知 |
| 弹幕读取/发送/点赞 | `internal/ipc/danmaku.go` | 迁移轨道布局、防重叠、播放时钟、seek、暂停、倍速以及发送反馈 |
| 弹幕设置及其它播放偏好 | 已有设置值和含义 | WebView localStorage 中的用户配置需要一次迁移，不能直接重置为默认值 |
| 全屏、媒体键、Now Playing、防休眠 | `internal/native/features.go` 已有能力 | 接到原生播放器状态；全屏和画中画往返不应改变会话、暂停意图或重复上报 |
| 画中画 | macOS AVPlayerView 提供系统能力 | MyGo v0.9.0 现有 VideoPlayer 公共接口未提供 PiP。现有按钮、P 键、菜单和恢复窗口行为需独立原型验证 |
| 氛围光 | 原生窗口已有颜色消费接口 | 现在通过 JS canvas 采样视频边缘；原生端需要帧采样或 GPU 处理，避免每帧把整幅画面拷贝回 CPU |

系统画中画有官方 AVKit 路径，但不能把“能显示视频”或“AVPlayerView 有 PiP”当作现有全部自定义控制已经等价实现。[Apple AVPlayerView 文档](https://developer.apple.com/documentation/avkit/avplayerview)

**影响选型的两个关键缺口**

第一，现有冷启动会优先把分片 MP4 交给浏览器 MediaSource，在完整 HLS 片段形成前启动播放，详见 `frontend/app.js` 的 `loadPlayback` 及 `frontend/progressive-media.js`。AVPlayer 不提供浏览器的 SourceBuffer 接口，不能机械搬运这套实现。改为只播放现有 HLS 可能延长冷启动；直接把同一分片 MP4 URL 交给 AVPlayer 是否能达到相同启动和跳转行为，需要用当前 MediaServer 的真实输出验证。

第二，v0.9.0 的 `Buffering()` 只报告是否在等数据，公开播放接口没有提供当前预加载决策所用的完整 buffered ranges，也没有提供 PiP 或底层 AVPlayer 访问入口。后端预加载状态中的 CachedSeconds 表示缓存产出，不等同于解码器已可播放的缓冲时长。为了保留缓冲条、弱网策略和连续切换体验，需要补齐这些信息。

**建议的实现结构**

原生 MyGo UI 负责控件、评论、弹幕和布局；Go 播放控制器统一管理当前剧/集、画质、播放位置、暂停意图、请求版本及前后预热；AVFoundation 负责音视频播放；已有 Go 服务继续负责媒体、缓存、账号和双向同步。

先在播放后端边界定义 play/pause/seek/rate/volume、状态与事件，避免界面直接依赖某一套播放器实现。正常画面与画中画应复用同一个播放会话和时钟。

| 路径 | 优点 | 需要补齐的部分 | 评价 |
| --- | --- | --- | --- |
| v0.9.0 `ui/video` 配合原生控件 | 与 MyGo 绘制和布局直接整合，基础音视频能力现成 | PiP、精细缓冲、后台首帧预热、氛围光采样的可访问能力 | 适合快速验证原生播放和基础性能；单靠现有公开 API 不足以宣布功能全部对齐 |
| v0.9.0 `ui.NativeView` 配合 AVPlayer/AVPlayerView 薄封装 | 可以直接管理系统播放器、缓冲和原生视图；macOS 官方 PiP 路径清楚 | 视图/播放器生命周期、回调、线程、键盘与系统 PiP 控制的等价入口 | 功能完整优先时更有控制力，建议作为原型中的重点路线 |

项目已经使用 purego/objc，可以评估沿用现有调用方式；也可以使用薄 Swift 模块。MyGo 的 native module 文档明确标注其为实验性，若采用生成模块，需要纳入版本固定及构建打包验证，不应默认没有集成成本。

迁移期间可保留旧播放后端作内部回退，待原生功能和性能验收后再切默认。最终版本需要删除播放器对 WebView 及 JS 播放时钟的依赖，后台也不保留一个用来承担播放功能的隐藏页面。

**收益判断**

| 维度 | 预期收益 | 判断边界 |
| --- | --- | --- |
| 状态一致性与维护 | 高 | 消除 MediaReady、Page.Eval、DOM 生命周期与 Go 状态间的一部分协调；取消、会话和网络并发保护仍需要保留 |
| 键盘、焦点、布局、无障碍 | 较高 | 原生输入和 UI 树更统一；弹幕、浮层及输入框仍须设计和验收 |
| 内存 | 有下降潜力 | 可减少 Web 内容运行时、DOM 和 JS 的开销；多个预热解码器、视频缓冲和 FFmpeg 的开销仍存在，不能直接给出节省量 |
| CPU/功耗 | 可能改善 | WebKit 本身也使用 AVFoundation，迁移不等于从软件解码变为硬件解码；预热策略和帧采样可能抵消收益 |
| 首帧、连续切换 | 可能提升，也可能回退 | 更直接控制播放器有利于调优，但当前 MSE 冷启动和首帧预热已做过优化，需要同素材对照 |
| 上游网络速度、解密成本 | 直接收益有限 | 移除 WebView 不会自动改变上游服务、内容密钥、解密和音画合并工作 |
| 应用包体积 | 不能预期大幅下降 | 当前是系统 WebView，并非应用随包携带整套 Chromium；原生桥接也可能引入构建产物 |
| 双向同步 | 减少上报链路层数 | 同步主体已在 Go，可靠性依赖正确接回所有上报时机，不能仅由“原生”保证 |

性能判断属于基于架构的推断，尚无本项目原生播放器对照数据。WebKit 的 AVFoundation 播放实现可参见 [官方源码](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/graphics/avfoundation/objc/MediaPlayerPrivateAVFoundationObjC.mm)。现有 FFmpeg 输出使用 `-c copy` 进行相应处理，移除 WebView 不代表能取消这段媒体工作。

**达到“不影响任何功能”的验收条件**

1. 同一设备、同一素材、同一网络分别测试冷缓存、暖缓存和完整缓存，记录首帧 P50/P95、切换等待、卡顿、掉帧、整个播放链路的内存与 CPU/功耗。不能只对比主进程而忽略 WebKit 或 FFmpeg。
2. 验证快速连续上下切换、反向切换、末集/跨季、切画质保集数和秒数、不同倍速、暂停后切换、弱网重试及离开播放页后的资源释放。
3. 验证评论/回复、收藏/点赞、弹幕发送/点赞/外观设置与旧配置迁移，尤其是 seek、暂停和倍速后的弹幕时间轴。
4. 真机验证全屏、系统媒体键、菜单、PiP 按钮与 P 键、小窗关闭/恢复及窗口焦点。PiP 内的叠加内容按现有行为逐项核对。
5. 验证暂停、换集、关闭、退出、账号切换后的持久化和双向同步。已有本地/云端冲突与账号隔离回归应继续通过。
6. 现有 Go 测试继续运行，同时把 JS 播放行为用例转为后端无关的控制器测试和原生媒体集成测试。现有 129 项 JS 回归通过不能代替新引擎验收。

**投入与推进建议**

按单名熟悉 Go 和 macOS 媒体的开发者估算：关键路径原型约 2–4 个工作日；完整功能迁移及真机回归建议按约 3–6 周预算。这是经验估算，需根据 PiP 等价控制及冷流启动原型结果调整。

第一阶段只验证三件事：现有媒体流的冷启动与 seek、连续切剧及预热、PiP 和窗口往返。通过后再迁移所有控件、互动和偏好，最后切换默认播放器。以功能和性能验收作为替换条件，能够把对现有使用的影响控制在迁移过程内部。

投入理由最充分的是播放器状态更可控、原生交互一致和长期维护；性能改善幅度应由第一阶段对照实验决定。
