## 可观察到的弯路及改进

| 操作问题 | 具体表现 | 后续执行约束 |
| --- | --- | --- |
| 重复审阅 | 整组 diff 输出截断后，又分文件读取多份已看过的 diff，并额外写临时文件 | 首次按模块分批审阅；后续只读疑点或新修改 |
| 监控方式反复切换 | watch 顶层调度器，停止后查询子构建，再重新 watch，同时另查子任务 | 一种监控方式，直接读取子任务的紧凑状态 |
| 错误判断排队 | 根据子运行列表的 queued 状态称还未开工，后查 job 记录显示源码验证已开始 | 依据 job/step 执行证据判断，证据不足就保留不确定性 |
| 无效命令往返 | 不存在的 Makefile 通配符、未结束运行的日志、不支持的 isLatest JSON 字段 | 确认路径，使用支持字段，按任务阶段查询 |
| 过早查询结果 | 构建未结束时查询 Release 得到 release not found | 发布 job 成功后集中检查一次 Release 与附件 |
| 汇报口径偏离 | 面对 42 分钟质疑，先强调 CI 只花约 11 分钟 | 优先回答总处理耗时，区分已知区间与记录缺口 |

这些记录证明存在低效操作，不证明每项浪费了多少分钟。下次保留开始处理、检查完成、
标签推送、公开发布、最终汇报的时间，才能判断改进是否减少了用户等待。

本轮本地 Go 测试 39 个包共 1130 项、Python 发布脚本 18 项均通过；远端三平台构建、
